Reference documentation

A sample reference covering the kinds of systems I build: wallets and payment flows, role-based access, member records and transaction ledgers, and storefront ordering. Endpoint shapes and conventions are drawn from real production work.

Base URLs, keys, and identifiers below are illustrative, not live credentials.

Authentication

Every request outside the public webhook receiver requires a bearer token issued at login. Tokens are short-lived; refresh tokens rotate on use.

Header
Authorization: Bearer <access_token>

Error handling

Errors follow a consistent envelope so client teams can handle failures generically instead of parsing message strings.

Response422 Unprocessable Entity

  "error": {
    "code": "INSUFFICIENT_BALANCE",

  }

POST /v1/wallets/:walletId/credit

Credit wallet

Queues a credit against a wallet. This does not write the balance synchronously: it enqueues a BullMQ job so a burst of concurrent credits can't race each other into an inconsistent ledger.

Body parameters

FieldTypeDescription
amountnumberAmount to credit, in minor units.
currencystringISO 4217 currency code.
idempotencyKeystringClient-generated key. Retried requests with the same key are deduplicated, never double-credited.
Request body
{
  "amount": 5000,
  "currency": "NGN",
  "idempotencyKey": "credit_7c1a"
}
202 response202 Accepted
{
  "jobId": "job_44de9a",
  "status": "queued"
}
POST /v1/webhooks/payment-provider

Payment provider webhook

Receives asynchronous payment confirmations. Signature-verified, then handed to the same queued credit path as the wallet credit endpoint, so a webhook retry from the provider is naturally idempotent.

Headers

HeaderDescription
X-SignatureHMAC-SHA256 signature of the raw request body.
POST /v1/trades

Execute trade

Executes a market order against the wallet's available balance. Validates funds synchronously; settlement and reward accrual happen through the job queue.

Member record model

The core record kept per member: identity, standing, and a running link to their transaction history. Designed so a member's full contribution history can be reconstructed from the ledger alone, not from denormalized totals.

FieldTypeDescription
memberIdstringStable identifier, independent of name or contact changes.
statusstringactive / lapsed / honorary.
joinedAtdateDate the member record was created.
ledgerBalancenumberDerived, not stored: computed from the transaction log at read time.
POST /v1/members/:memberId/transactions

Record transaction

Appends a transaction to a member's ledger. Transactions are append-only: corrections are made with a reversing entry, never by editing or deleting a past record, so the history stays auditable.

Request body
{
  "type": "contribution",
  "amount": 10000,
  "note": "2026 annual dues"
}
201 response201 Created
{
  "txId": "tx_5e01b3",
  "balanceAfter": 42000
}
GET /v1/members/:memberId/transactions

Transaction history

Full, paginated transaction history for a member. The same endpoint powers both the member's own view and the association's transparency reporting.

Query paramTypeDescription
limitnumberMax results per page. Default 20, max 100.
fromdateOptional. Filters to transactions on or after this date.
POST /v1/orders

Place order

Creates an order from a cart. No account or login required: the buyer supplies a phone number, which becomes the lookup key for tracking the order afterward.

Request body
{
  "phone": "+234801XXXXXXX",
  "items": [
    { "sku": "rice-50kg", "qty": 2 }
  ]
}
201 response201 Created
{
  "orderNumber": "ORD-7841",
  "status": "pending"
}
GET /v1/orders/lookup

Look up order

Looks up an order by phone number or order number, the two paths a guest checkout customer has back into their order status.

Query flow

01

Buyer submits phone or order number

Either value alone is enough to resolve an order; no account, email, or password involved.

02

Server resolves the most recent matching order

If a phone number matches multiple orders, the most recent is returned with a link to view others.

03

Status and items are returned

No account data beyond what's needed to identify the order is exposed in the response.
